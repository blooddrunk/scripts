# 运维记录:2026-10 路由器双网接入、上行切换与自建 DERP 中继 mesh

本文记录 2026-10-26 ~ 10-27 三件事的完整排查与处置:路由器停留在备用网络、
上行变更导致全网离线(含 passwall2 分流方案)、自建 DERP 中继交叉组网。
环境:GL-MT3600BE(OpenWrt 25.12.5 / GL.iNet 4.9.1,tailscale 1.92.5)、
Nosla VPS(82.139.215.223,实为 xTom 法兰克福,CN 出口 IP)、
Bitsflow VPS(216.23.86.169,BITSFLOWCLOUD 东京)、
Headscale 0.29.3 ×2(`hs-nosla.haoqi90.top` 主 / `hs-bitsflow.haoqi90.top` 备)。

## 事件一:路由器"未按预期加入两个网络"(10-26)

### 现象

用户视角:路由器没有如预期加入两个 headscale。服务端视角:nosla(主)
上路由器节点 offline,自 10-02 起 last seen 不更新。

### 排查路径与证据

1. 路由器端 `tailscale status` 正常 Running,但 ControlURL 是**备用网**
   bitsflow;`tailscale switch --list` 显示两个身份都在
   (3e3e=nosla、b66e=bitsflow),UCI 登记表、subnet、site-to-site、
   failover 配置全部就绪——不是"没加入",是**活动网络不对**。
2. 关键反证:bitsflow 侧路由器节点的 last seen 停留在切换那一刻
   (10-26 11:22:06 UTC)。如果 watchdog 后来又切回过 bitsflow,该时间
   会更新——据此排除"反复切换",锁定"切过去之后一直没回来"。
3. 两台 headscale `/health` 均 200,服务端日志无异常。
4. watchdog 运行态(`no-switch current=bitsflow`)与健康计数(ok 31/32)
   表明:当前网健康、无需切换。默认 `failback=false`,切走后保持稳定。

### 根因

10-02 前后 nosla 短暂不可达(具体触发已不可考:watchdog 决策日志在
tmpfs,重启即清),watchdog 按设计切到 bitsflow;`failback=false` 使其
一直停留在备用网。是"缺少一次回切",不是故障。

### 处置与验证

```sh
cd /root/headscale-openwrt-bootstrap
./tailscale-openwrt.sh --login-server https://hs-nosla.haoqi90.top switch-to
./tailscale-openwrt.sh enable-failover --failback true   # 此后主网恢复自动回切
```

验证:nosla 侧节点 online、路由 192.168.8.0/24 Approved+Serving;
site-to-site 偏好完整保留(RouteAll=true、CorpDNS=false);fw4 双向
转发在;脚本 `status` 输出 OK 无 FAIL。数据面:无物理链路的 qi 站点
192.168.6.1 经 tailnet ping 通(0% 丢包,DERP 中继路径);
192.168.10.0/24 由两站点间 eth0 物理直连承载(1.7ms,tailscale 对已
存在的静态路由让位,属合理共存)。

## 事件二:上行变更导致路由器两网全离线(10-27)

### 现象

09:37(北京)起路由器在**两个** tailnet 上同时 offline,远程管理不可达。

### 证据链(层层收窄)

| 步骤 | 观察 | 推论 |
| --- | --- | --- |
| 两台 VPS 节点列表 | bitsflow last seen 仍是 10-26 11:22,nosla 停在 10-27 01:37 UTC | 没有发生切换;路由器单点失联 |
| 路由器 `ip addr`(现场手机 SSH) | eth0 从 `192.168.10.226` 变为 `172.17.50.238/22` | 上行物理变更(WAN 从 192.168.10.1 那台路由器改插公司网口) |
| 路由器探测 | `ping 223.5.5.5` 通、DNS 解析正确 | 新上行有互联网、DNS 正常 |
| `curl https://hs-*.haoqi90.top/health` | 两台都返回 000 | 公司网封了到两台 VPS 的 TCP 443 |
| 对照测试 | `curl https://www.baidu.com` = 200 | 公司网按目标放行国内 TCP,非全断 |

ICMP 到 VPS 是通的(82.139.215.223 通,145ms)——最具迷惑性的一点:
**ping 通不代表控制面可用**,tailscale 控制面/DERP 全部走 TCP 443。
BusyBox `ping -s 1400` 不置 DF 位,大包可能分片通过,不能排除 MTU
问题,需用 `nc`/curl 握手测试区分(注意 BusyBox nc 不支持 `-w`,
传参会直接打印用法)。

### 根因

WAN 插到公司网口;公司网出站防火墙只放行国内 TCP,两台 VPS 的 443
均被拦。tailscaled 报 `fetch control key: context deadline exceeded`、
health 显示 logged out/NoState,都是**控制面不可达的表象**——
`debug prefs` 里 ControlURL 仍在即证明身份与配置完好,无需重注册。

### 处置

路由器上有 passwall2,让控制面流量走代理(daed 在 192.168.10.1 上的
配置里,tailscale 直连规则已被注释、控制面域名实际走 fallback proxy,
因此在旧上行上这套共存方式已被验证)。passwall2 侧规则(注意仓库
README 记过的坑:**"端口"字段会 AND 进每一条规则,域名与端口必须拆成
两条规则**,不该填的字段严格留空):

| 规则 | 域名 | 端口 | 协议 | 出站 |
| --- | --- | --- | --- | --- |
| tailscale-ctrl-proxy | `tailscale.com`、`hs-nosla.haoqi90.top`、`hs-bitsflow.haoqi90.top` | 留空 | tcp,udp | 代理节点 |
| tailscale-stun-direct | 留空 | `3478` | 仅 udp | `_direct` 直连 |

前置条件:passwall2 开启**本机代理**(否则 tailscaled 出站根本不经过
passwall2,规则全无效——最易漏的一步);流量嗅探保持开启(tailscaled
按 IP 直连,域名规则靠 TLS SNI 命中)。

规则生效后路由器曾短暂回线(last seen 15:57),其后仍不稳定——公司
上行对代理节点端口的可用性存疑,根因仍是**这条上行不适合承载 tailnet**。

### 结论与边界

- 上游防火墙封锁无法在路由器侧绕过,要么经代理(如上),要么换回
  无限制上行。插回 192.168.10.1 后无需任何手动操作,watchdog 自动
  恢复 nosla(failback 已开启)。
- 公司上行下 P2P 直连大概率不可用(对外 UDP 不友好),流量经 DERP
  中继兜底;该场景见下文自建 DERP。
- 应急排查命令包(现场手机 SSH 直接可用):

```sh
/usr/sbin/tailscale status
/usr/sbin/tailscale debug prefs | grep -i controlurl
ip addr show eth0 | grep -E 'state|inet '
ping -c 3 -W 3 223.5.5.5
curl -sk --max-time 6 -o /dev/null -w '%{http_code}\n' https://hs-nosla.haoqi90.top/health
logread | grep tailscale-failover | tail -10
```

## 项目:自建 DERP 中继交叉组网(10-27)

### 背景

长期观察:tailnet 走东京中继时抖动。摸底发现:

- 两台 VPS 的 embedded DERP **早已启用**(`enable-derp` 曾执行过,
  state.json `embedded_derp: true`),`/derp/probe` 均 200——中继可用;
- 但 `derp.urls` 仍保留官方 map,客户端按实测延迟自动选路:
  官方东京(~60ms)恒赢 nosla 中继(实测法兰克福,国内到它 147ms),
  自建 region 永远轮不上,抖动来自**共享的官方东京中继**;
- bitsflow 中继(东京、独享、实测 43ms)是真正有价值的资产,但
  原本只对 bitsflow tailnet 自己的成员可见;
- STUN UDP 3478 两台 VPS 都被**云平台安全组**拦截(宿主机 nft INPUT
  policy accept,堵在面板那一层),不影响 443 中继,但 NAT 探测缺失。

### 方案

每个 tailnet 配齐两个自建 region,并移除官方 map:

| tailnet | 下发 region | 角色与实测延迟(国内视角) |
| --- | --- | --- |
| nosla(主) | 999-nosla(法兰克福) + **901-tokyo(bitsflow)** | 主中继 tokyo 42.5ms,备援 nosla 147.3ms |
| bitsflow | 999-bitsflow(东京) + 902-fra(nosla) | 主中继 bitsflow 43.3ms,备援 fra 153.9ms |

配套决策与代价:

- **移除官方 map**(README 已记录该取舍:失去第三方灾备,换取全部
  中继流量走独享线路);
- **`verify_clients: false`**(embedded DERP 只服务本 tailnet 成员的
  校验放开,交叉使用对方中继所必需;代价是中继开放,理论可被外部
  消耗带宽,与官方公共中继同款风险)。

### 配置方法(两台镜像)

1. 新建 `/etc/headscale/derp-extra.yaml`(nosla 侧示例;bitsflow 侧
   交换 region 与域名即可):

```yaml
regions:
  901:
    regionid: 901
    regioncode: tokyo
    regionname: "Bitsflow Tokyo (self-hosted)"
    nodes:
      - name: 901a
        regionid: 901
        hostname: hs-bitsflow.haoqi90.top
        ipv4: 216.23.86.169
        canport80: false
```

2. `/etc/headscale/config.yaml` 三处修改:

```yaml
derp:
  server:
    verify_clients: false   # 原 true;放开跨 tailnet 使用
  urls:
    # - https://controlplane.tailscale.com/derpmap/default  # 注释掉=移除官方 map
  paths:
    - /etc/headscale/derp-extra.yaml   # 填入打包配置自带的空 paths: []
```

3. 事务流程照旧:备份 → `headscale configtest` → `systemctl restart
   headscale` → 验证 `/health` 与 `/derp/probe` 200。

备份文件:`/etc/headscale/config.yaml.bak-derpmesh-20261027-084116`
(nosla)、`config.yaml.bak-derpmesh-20261027-174307`(bitsflow)。

### 踩坑记录(排查用时最长的一段)

- **`configtest` 不校验 `paths` 指向的文件内容**——它只验证配置本身;
  derp-extra.yaml 是运行时才加载的。所以"configtest 通过"不能作为
  map 生效的证据,必须用客户端实测 `tailscale debug derp-map`。
- 打包配置在 `derp:` 节内**自带一个 `paths: []`**,手工再插入一个
  `paths:` 键会 YAML duplicate key,configtest 直接 FTL。正确做法是
  填写自带的那一个。
- `verify_clients` 实际缩进是 4 空格(`derp.server` 下两层),sed
  匹配时注意。
- **临时客户端验证的登录陷阱**(本次最耗时):在 VPS 的 root shell 里
  无论 `tailscale up --login-server` 还是 `tailscale login
  --login-server`,ControlURL 始终为空、注册请求发往官方
  `controlplane.tailscale.com`,报 `invalid key: unable to validate
  API key`(headscale 的 key 发给了官方服务器)。同一二进制
  (1.92.5)、同一命令在干净环境(本地 WSL)一次成功。结论:在新
  环境做 headscale 注册验证时,优先在干净的机器上跑临时客户端;
  daemon 日志里 `control: control server key from <URL>` 一行可直接
  判定实际注册目标。
- 验证 DERP map 无需常驻节点:下载静态 tailscale 到 /tmp,
  `tailscaled --tun=userspace-networking --socket=...` + 一次性
  preauthkey(`headscale preauthkeys create --user 1 ...`,注意
  0.29.x 的 `--user` 要传数字 ID),`debug derp-map` + `netcheck`
  读完即 `logout` 并 `headscale nodes delete --identifier <id>
  --force`,零残留。

### 验证结果

临时客户端实测两网 map 与延迟:

```text
nosla tailnet:   901 tokyo  hs-bitsflow.haoqi90.top  42.5ms
                 999 nosla  hs-nosla.haoqi90.top     147.3ms
bitsflow tailnet:999 bitsflow hs-bitsflow.haoqi90.top 43.3ms
                 902 fra    hs-nosla.haoqi90.top     153.9ms
```

在线节点(手机/lightlayer)在 headscale 重启后重新拉取 netmap 正常。
国内视角两个 tailnet 的中继兜底均为独享东京 ~43ms。

### 待办

      补全自建 region 的 STUN/NAT 探测(中继本身不受影响)。
- [ ] 路由器恢复可靠上行后执行 `/usr/sbin/tailscale netcheck`,确认
      只见 tokyo/nosla(bitsflow/fra)自建 region;插回 192.168.10.1

- [ ] 观察公司上行 + passwall2 的稳定性,决定是否长期使用该上行。

### 回滚

## 事件三:approve-route"无法 Serving"与路由器自持架构改造(10-27 晚)

### 现象

`headscale-vps.sh approve-route --node-id 8 --route 192.168.8.0/24` 后,
路由表 Approved/Available 有值但 **Serving 恒空**;node 8 反复离线。

### 排查路径与证据(timeline)

| 时间(北京) | 观察 | 推论 |
| --- | --- | --- |
| 15:57 | nosla 日志 node 8 断开,此后零重连;16:16 被清理出 netmap | Serving 需要节点在线,approve 本身已成功(数据库标记完好) |
| 18:49 | WAN 插回 192.168.10.1 的 LAN(192.168.10.226),路由器重启(此前疑死机,pstore 空、无持久日志) | 两个 tailnet 均离线的原因在上行,不在服务端 |
| 18:53 | 节点上线,Serving 自动恢复;P2P 直连正常(home 6ms) | 服务端零操作即可自愈,验证"approve 持久" |
| 19:1x | 关闭 m-w-r 的 daed 做自持测试:裸 443 到两台 VPS 全部超时;passwall2 域名分流(_default→reality 链)时通时断 | daed 此前一直在兜底承载控制流量 |
| 19:2x | reality 链 socks 单测良好(0.33s),但透明拦截路径必死 | 问题不在链路,在拦截层 |
| 19:3x | `nft list ruleset` 定谳:代理服务器 IP 集合 `{82.139.215.223, 216.23.86.169}` 整体 return(防回环),优先级高于一切 shunt 规则 | **终极根因**,见下 |

### 根因

passwall2 为防回环,把**所有已配置代理节点的服务器 IP**排除在透明
拦截之外(整 IP,不限端口)。本项目把 reality/hysteria2 节点架在
Headscale VPS 本机上,于是控制域名解析出的 IP 恰好命中排除集合——
透明拦截+域名分流的方案**在原理上永远接不住** tailscale 控制流量;
能通全靠 m-w-r 的 daed 按 SNI 兜底。公司上行封 443 后,daed 一关,
控制面无路可走。

### 处置(方案:tailscaled 显式走 socks,快照见 backups/gl-mt3600be/)

1. `/etc/init.d/tailscale-core`(GL 固件的真正 init 名!)加
   `procd_set_param env ALL_PROXY=socks5://127.0.0.1:1081`——域名由
   socks 远端解析,绕开排除集合;TCP-only,不影响 UDP 打洞;
2. `/etc/init.d/tailscale-failover` 加同路径的
   `https_proxy=socks5h://...`——watchdog 探测必须与 tailscaled 同路,
   否则裸探测必失败→误切换;
3. 踩坑两则:①`uci add_list` 写本是非列表的 `dns_hosts` 会把它变成
   多元素列表,passwall2 init 直接解析失败(启动报错),须整段
   `uci set` 或用备份还原;②`/etc/init.d/tailscale` 是 GL 固件残留
   文件(重启即消失),daemon 真正由 `tailscale-core` 管理,env 加
   在那里,用 `cat /proc/$(pgrep tailscaled)/environ` 验证生效。

### 验证结果(全绿)

- nosla:node 8 online,192.168.8.0/24 三列齐平;
- 控制面:tailscaled→127.0.0.1:1081(reality)→nosla 出口;60s soak
  3/3 200(0.35–0.59s);
- P2P:home 直连 7ms(UDP 不走 ALL_PROXY);
- watchdog:no-switch current=nosla;
- 代价:DERP 中继经法兰克福出口(~470–880ms);中继慢的另一头在
  qi 侧(所有 peer 经 DERP 到 qi 均 ~680ms,qi 密码不同,待查)。

### 连带影响与遗留

- **关闭 daed 会把 m-w-r 自己(node 10)和 WORK-PC(node 13)打下线**:
  两者的 tailscale 控制面/DNS(DoH)原本由 daed 承载,daed 一关,
  m-w-r 的 DNS 把 hs-* 解析到 192.200.0.x 污染地址。gl 已不依赖
  daed;m-w-r 需要恢复 daed 或做同款自持改造。
- reality(TCP)在公司网有周期性闪断(分钟级,自动重拨可容忍);
  升级位:socks 1081 换 nosla-hysteria2(UDP 51237,全天稳定),
  一行 uci,见备份 README。
- 路由器无持久日志,死机取证靠人;建议开启 logd 落盘或远程 syslog。

### 回滚

见 `backups/gl-mt3600be/20261027-selfcarry/README.md`(完整快照+
两条 sed 快速回退 env)。

## 经验汇总

1. "路由器离线"先分诊:**切换**(看两台 last seen 哪台更新过)vs
   **单点失联**(两边都不更新)vs **身份丢失**(`debug prefs` 的
   ControlURL 是否还在)。三种情况的处置完全不同。
2. 网络排查三角定位:ICMP(路由通否)、DNS(解析对否)、TCP 443
   (服务可达否)三者独立,逐一测;ping 通 VPS 不代表控制面可用。
3. 上游防火墙封锁只能在更上游解决(换上行或经代理);路由器侧一切
   配置无需变动,身份在 `tailscaled.state` 里不会因断网丢失。
4. 自建 DERP 的价值取决于**地理位置**:客户端永远选延迟最低的
   region,147ms 的法兰克福救不了原本走 60ms 官方东京的 tailnet;
   同城的独享中继(43ms)才是替换方案。每个 tailnet 只含自己那台
   embedded region 时,交叉组网(`derp.paths` 本地 map)才能把对的
   中继放进来。
5. DERP 只是兜底路径质量;P2P 直连是否可用取决于上行(UDP 可达性、
   STUN 3478),抖动治本还得看上行。
6. passwall2 防回环会把**代理节点服务器 IP**整体排除在透明拦截之外,
   且优先级高于任何 shunt 规则。代理节点与控制面同机部署时,
   "透明拦截+域名分流"原理上必然失效;正解是 tailscaled 显式走
   socks(`ALL_PROXY`),域名交给代理远端解析。
7. 改代理配置的 uci 纪律:`add_list` 只能用于真列表选项(先
   `uci show` 确认);动配置前先 `cp` 备份,出问题整体还原比增量修快。
8. 透明代理的"兜底承载"具有**双向依赖**:gl 曾依赖 m-w-r 的 daed,
   而 m-w-r 自己的控制面也依赖 daed。关停任何一层前,先问"谁在这层
   上面",否则救一个倒两个(node 10/13 连带 offline 即教训)。
